# Git 컨벤션 가이드

> 원문 출처: [Notion Git 컨벤션](https://app.notion.com/p/Git-412cf10cd2e780a4aceac385a55d4fae)

프로젝트 개발 시 브랜치 생성, 커밋 작성, Pull Request(PR) 생성 과정에서 준수해야 하는 공식 Git 컨벤션입니다.

---

## 1. Branch Convention (브랜치 컨벤션)

### 기본 원칙 (GitHub Flow)

- 작업 브랜치는 `main`에서 생성하고, 작업 완료 후 `main`으로 PR을 생성합니다.
- `main`은 배포 가능한 최종 브랜치로 관리합니다.

### 네이밍 규칙

- 브랜치명은 `<type>/<description>` 형식으로 작성합니다.
- `description`(작업 내용)은 소문자 영어와 하이픈(`-`)을 사용합니다.
- 한 브랜치에는 하나의 목적만 담습니다.

```text
<type>/<description>
```

**예시**:

- `feature/oauth2`
- `style/responsive-layout`
- `fix/login-token-refresh`

### 브랜치 타입 (7종)

| 타입       | 설명                                                             |
| ---------- | ---------------------------------------------------------------- |
| `feature`  | 새로운 기능 구현 (커밋의 `feat`와 달리 `feature` 전체 단어 사용) |
| `style`    | 코드 스타일 및 포맷팅 수정                                       |
| `fix`      | 버그(기능) 수정                                                  |
| `refactor` | 리팩토링                                                         |
| `docs`     | README 등 문서 작업                                              |
| `test`     | 테스트 코드, 실험, 기타 검증 작업                                |
| `design`   | CSS, UI 디자인, 이미지 등 화면 관련 수정                         |

## 2. Commit Convention (커밋 컨벤션)

### 기본 원칙

- 커밋 메시지는 `<type>: <subject>` 형식으로 작성합니다.
- 제목(`subject`)은 변경 내용을 명확하게 설명하되, 한 줄로 간결하게 작성합니다.
- **`feat` 타입을 사용할 때는 "~기능 추가"가 아니라 "~기능 구현"으로 작성합니다.**
- 이슈와 연결되는 작업은 제목 끝에 이슈 번호(` #<issue-number>`)를 붙입니다.

### 작성 형식

```text
<type>: <subject> #<issue-number>

<body>
```

- `type`: 변경 유형
- `subject`: 커밋 제목
- `issue-number`: 관련 이슈 번호가 있을 때만 작성
- `body`: 필요한 경우 변경 내용을 목록으로 작성

### 커밋 타입 (12종)

| 타입       | 설명                                                     |
| ---------- | -------------------------------------------------------- |
| `feat`     | 새로운 기능 구현                                         |
| `fix`      | 버그 수정                                                |
| `docs`     | 문서 수정                                                |
| `style`    | 코드 포맷팅, 세미콜론 누락 등 코드 동작 변경이 없는 수정 |
| `refactor` | 코드 리팩터링                                            |
| `test`     | 테스트 코드 추가 또는 수정                               |
| `chore`    | 빌드 설정, 패키지 매니저, 기타 환경 설정 수정            |
| `comment`  | 필요한 주석 추가 또는 수정                               |
| `design`   | CSS, UI 디자인, 이미지 등 화면 관련 수정                 |
| `remove`   | 파일 또는 코드 삭제                                      |
| `rename`   | 파일 경로 또는 파일명 변경                               |
| `devops`   | 배포, CI/CD 및 프로젝트 자동화 관련                      |

### 커밋 예시

```text
feat: OAuth2 기능 구현 #1

- access token 갱신 기능 구현
- 로그인 성공 후 사용자 정보 저장 처리
```

## 3. PR Convention (PR 컨벤션)

### PR 타입 (9종)

| 타입       | 설명                                                        |
| ---------- | ----------------------------------------------------------- |
| `feat`     | 새로운 기능 추가 또는 기존 기능 개선                        |
| `fix`      | 버그 수정 (서버 오류, 데이터 불일치 등)                     |
| `docs`     | 프로젝트 문서 수정 및 추가 (README.md 등)                   |
| `style`    | 코드 포맷팅, 세미콜론 누락 등 기능과 무관한 스타일 수정     |
| `design`   | CSS, UI 디자인, 이미지 등 화면 관련 수정                    |
| `refactor` | 기존 코드 및 아키텍처 개선 (리팩토링)                       |
| `test`     | 유닛 테스트, 통합 테스트 코드 추가 및 수정                  |
| `chore`    | 개발 환경 구축 및 설정 변경 사항 (빌드, 의존성 업데이트 등) |
| `devops`   | 배포, CI/CD 및 프로젝트 자동화 관련                         |

### PR 제목 형식 및 예시

- **형식**: `<type>: <subject>`
- **예시**: `feat: OAuth2 기능 구현`
